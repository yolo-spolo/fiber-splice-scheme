# Доменные документы

Как инженерные скиллы читают доменную документацию этого репозитория.

## Перед исследованием кода прочитать

- **`GLOSSARY.md`** в корне репозитория, или
- **`GLOSSARY-MAP.md`** в корне, если он есть: он указывает на `GLOSSARY.md`
  каждой области. Читайте те, что относятся к теме.
- **`docs/adr/`**: читайте ADR, касающиеся той области, где собираетесь
  работать. В многообластных репозиториях смотрите ещё
  `src/<область>/docs/adr/`.

Если этих файлов нет — **продолжайте молча**. Не сообщайте об их отсутствии и не
предлагайте создать их заранее. Скилл `/domain-modeling` (доступен через
`/grill-with-docs` и `/improve-codebase-architecture`) создаёт их по мере
надобности, когда термины или решения действительно появляются.

## Структура файлов

Одна область (большинство репозиториев):

```
/
├── GLOSSARY.md
├── docs/adr/
│   ├── 0001-event-sourced-orders.md
│   └── 0002-postgres-for-write-model.md
└── src/
```

Несколько областей (признак — `GLOSSARY-MAP.md` в корне):

```
/
├── GLOSSARY-MAP.md
├── docs/adr/                          ← решения на весь проект
└── src/
    ├── ordering/
    │   ├── GLOSSARY.md
    │   └── docs/adr/                  ← решения области
    └── billing/
        ├── GLOSSARY.md
        └── docs/adr/
```

## Пользуйтесь словарём глоссария

Когда ваш результат называет доменное понятие (в заголовке задачи, предложении
рефакторинга, гипотезе, названии теста), используйте термин в том значении,
которое даёт `GLOSSARY.md`. Не уходите в синонимы, которых глоссарий избегает.

Если нужного понятия в глоссарии нет — это сигнал: либо вы придумываете язык,
которого в проекте нет (передумайте), либо есть настоящий пробел (заметьте его
для `/domain-modeling`).

## Сообщайте о конфликтах с ADR

Если ваш результат противоречит существующему ADR, скажите об этом явно, а не
переопределяйте молча:

> _Противоречит ADR-0007 (событийные заказы), но стоит переоткрыть, потому что…_
